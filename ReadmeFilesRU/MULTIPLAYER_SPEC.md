# 🛰️ Спецификация сетевой архитектуры, P2P, LAN и Выделенных Серверов (MULTIPLAYER_SPEC.md)

Настоящий документ содержит исчерпывающее техническое и алгоритмическое описание сетевой архитектуры проекта. Сетевой стек полностью переписан: оригинальный lockstep-код DOS Doom (где игра ждала ввода от каждого игрока и зависала при малейшем пинге) полностью удален. 

Новая система использует асинхронную обработку сетевых прерываний ядра **KINII** под управлением рантайма `void.run`, совмещая три режима подключения: кооперативные P2P-комнаты с пробросом NAT (**Borderlands 2**), классическую локальную сеть (**LAN**) и авторитарную модель высоконагруженного выделенного сервера (**Battlefield / Fallout 76**).

---

## 🏗️ 1. Системные и архитектурные связи

Сетевая подсистема является главной транспортной артерией проекта и завязана на следующие модули:
* **Защита пакетов трафика:** Генерация сессионных ключей шифрования для сетевого потока происходит внутри изолированной памяти Ghost-RAM через [memory.ctos](../Lang_for_my_decisions/memory.ctos).
* **Синхронизация инвентаря:** Передача данных о торговле, поднятом луте и транзакциях координируется со спецификацией [INVENTORY_SPEC.md](./INVENTORY_SPEC.md).
* **Стриминг чата и мост:** Текстовые пакеты игрового и гильдейского чата перехватываются и дублируются на бэкенд [bridge.ctos](../Lang_for_my_decisions/bridge.ctos).
* **Трансляция GPS-координат:** Пакеты телеметрии игроков и орд монстров для вывода на смартфон отправляются по алгоритмам из [MAP_SPEC.md](./MAP_SPEC.md).

## 🌐 2. Три режима сетевой топологии (P2P, LAN, Dedicated)

Система поддерживает три различных сценария развертывания игрового мира. Сетевые пакеты для всех режимов унифицированы, но методы сопряжения клиентов различаются.

```

                              [ РЕЖИМЫ ПОДКЛЮЧЕНИЯ ]:

1. LAN (Локальная сеть)───> Сырые UDP-бродкасты ────> Прямое сопряжение в подсети
2. P2P (Listen Server)─> net.raw_inject+STUN/TURN─>Пробой NAT(Без настройки портов)
3. Dedicated Server─>Авторитарный void_win.exe─>Масштаб Battlefield (До 64 игроков)

```

### 2.1 Классическая локальная сеть (LAN Mode)
* **Принцип работы:** Режим предназначен для игры внутри домашней сети или компьютерных клубов без обязательного доступа к интернету.
* **Поиск серверов:** Клиент UZDoom отправляет сырой широковещательный UDP-пакет (Broadcast) на порт `5029` в локальную подсеть (например, `192.168.1.255`). Хост, поймав этот пакет, возвращает структуру метаданных сервера (Имя, текущий чанк открытого мира, количество игроков). Подключение происходит напрямую по локальному IP-адресу.

### 2.2 Кооперативные P2P комнаты (Listen Server / Borderlands 2 Style)
* **Принцип работы:** Один из игроков нажимает «Создать сетевое лобби». Его игра одновременно становится и клиентом, и сервером (Listen-хост). Графика Vulkan/OpenGL обрабатывается параллельно с сетевой логикой.
* **NAT Traversal (Технология net.raw_inject):** Главная проблема P2P-игр — закрытые порты у игроков (серые IP-адреса). Чтобы игроки подключались без настройки роутера, KINII задействует низкоуровневый инжектор сокетов. Он выполняет UDP Hole Punching (пробитие NAT) через сигнальный сервер `deploy_hub.vc`. Если прямое соединение физически невозможно, рантайм прозрачно переключает трафик на TURN-реле, сохраняя соединение лобби.

### 2.3 Выделенный консольный сервер (Dedicated Server / Battlefield Style)
* **Принцип работы:** Запуск бинарника через консоль ОС: `void_win.exe --server --port 5029`. Движок полностью отключает подсистемы рендеринга звука и видео. Нагрузка идет исключительно на процессорные ядра и сетевую карту.
* **Авторитарность:** В отличие от P2P, где хост верит клиентам, выделенный сервер является единственным источником правды. Он симулирует весь открытый мир, проверяет коллизии стен из [WORLD_DESIGN.md](./WORLD_DESIGN.md) и подтверждает легитимность выстрелов.

## ⚡ 3. Алгоритмы компенсации задержек и синхронизации (Netcode)

Для обеспечения идеальной регистрации попаданий (хитдетекта) и плавного перемещения на высоких скоростях, в сетевое ядро интегрированы три алгоритма:

### 3.1 Предсказание на стороне клиента (Client-Side Prediction)
Когда игрок нажимает клавишу движения `W`, локальный клиент UZDoom не ждет ответа от сервера (который придет через величину пинга, например, 60мс), а мгновенно передвигает физическую оболочку персонажа на экране. 
Каждому шагу присваивается инкрементальный номер тика `tick_id`. Когда от сервера приходит авторитарный пакет с позицией, клиент сверяет координаты. При расхождении менее чем на 4 юнита движок плавно корректирует позицию; при большем расхождении (чит или жесткий лаг) — жестко возвращает игрока назад.

### 3.2 Отмотка времени сервера (Lag Compensation / Назад в прошлое)
Если игрок с пингом 100мс стреляет из Borderlands-снайперки точно в голову бегущему монстру, на сервере этот монстр уже сместился вперед на 100мс, и выстрел бы прошел мимо. 
* Чтобы этого не происходило, сервер хранит циклический буфер позиций всех сущностей за последние 200 миллисекунд.
* При получении пакета выстрела `NET_CL_SHOT`, сервер считывает точный таймстемп отправки, «отматывает» позицию хитбокса монстра на 100мс назад и проверяет вектор луча. Если в тот момент прицел был наведен верно — урон засчитывается.

## 📦 4. Бинарная структура сетевого пакета (Network Packet Layer)

Все типы сетевых пакетов выровнены по границе 4 байт и имеют строгий заголовок для минимизации оверхеда трафика.

```void
struct NetPacketHeader {
    u32 magic_bytes;        // Идентификатор протокола (0x4B494E49 = "KINI")
    u16 packet_type;        // Тип пакета (0x01 = Движение, 0x02 = Выстрел, 0x03 = Чат)
    u32 tick_id;            // Номер игрового тика
    u32 player_network_id;  // Сетевой ID отправителя
    u32 packet_crc;         // Контрольная сумма пакета, зашифрованная ключом из Ghost-RAM
}

struct NetPlayerUpdatePacket {
    NetPacketHeader header; // Заголовок пакета (20 байт)
    f32 position_x;         // Координата X
    f32 position_y;         // Координата Y
    f32 angle_look;         // Угол поворота камеры (направление взгляда)
    u32 current_weapon_uuid;// UUID оружия в руках (верифицируется инвентарем)
    u8  buttons_mask;       // Битовая маска нажатых клавиш (W, A, S, D, Fire, Use)
}
```

## 🛡️ 5. Анти-чит и верификация сетевого состояния

Сетевой код KINII защищает сессию от распространенных сетевых эксплойтов:
1. **Защита от SpeedHack:** Сервер проверяет дельту расстояния между пакетами `position_x/y` за единицу времени. Если расчетное перемещение превышает максимальную скорость, установленную маской перков в [CLAN_SPEC.md](./CLAN_SPEC.md), пакет отбрасывается, а игрока телепортирует обратно.
2. **Защита от Replay-атак:** Если читер перехватит пакет успешного открытия сундука из [INVENTORY_SPEC.md](./INVENTORY_SPEC.md) и попытается отправить его повторно, сервер заблокирует транзакцию, так как `tick_id` пакета окажется устаревшим или дублирующим уже обработанный индекс.
