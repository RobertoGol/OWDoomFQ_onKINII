# 💰 Спецификация подсистемы инвентаря, экономики и торговых операций (INVENTORY_SPEC.md)

Настоящий документ содержит исчерпывающее техническое и архитектурное описание подсистемы инвентаря, экономики и проведения торговых сделок. Система спроектирована на стыке трех игровых концепций: персистентного сбора хлама и разбора предметов из **Fallout 4**, процедурно-генерируемых модификаторов и индексов редкости оружия из **Borderlands 2**, а также глобального выносного склада ресурсов и материалов снабжения из **State of Decay 2**.

Главная цель данной подсистемы — обеспечить 100% персистентность (сохранность) имущества игрока, связать инвентарь внутри игры с мобильным приложением-компаньоном и полностью исключить возможность читерства (дюп предметов, подмена памяти) как в кооперативном, так и в серверном мультиплеере.

---

## 🏗️ 1. Системные и архитектурные связи

Подсистема инвентаря не является изолированной и опирается на низкоуровневые модули ядра **KINII** и скрипты игрового движка через систему перекрестных ссылок:
* **Изоляция в ОЗУ:** Списки активных предметов игрока во время сессии удерживаются в зашифрованной памяти Ghost-RAM, контролируемой файлом [memory.ctos](../Lang_for_my_decisions/memory.ctos). Любые попытки сканирования памяти сторонними утилитами блокируются.
* **Постоянное хранение:** Все изменения инвентаря, факты траты патронов или разбора хлама записываются транзакционными дельта-патчами в скрытые сектора накопителя `HiddenVault` с помощью движка данных [sql.core](../Lang_for_my_decisions/sql.core).
* **Процедурная генерация:** При обыске контейнеров или убийстве боссов параметры оружия вычисляются лут-движком из файла [world_stream.void](./world_stream.void) и упаковываются в байтовую структуру предмета.
* **Визуализация на Android:** Отображение предметов, иконки редкости и интерфейсы торговли внутри мобильного мессенджера рендерятся через шаблоны разметки в папке [View/](../Lang_for_my_decisions/View/).

## 📊 2. Бинарная структура данных предмета (Item Serialization)

Каждый объект, находящийся в инвентаре игрока, описывается строго фиксированной структурой данных размером 32 байта. Это гарантирует высокую скорость чтения/записи и предотвращает уязвимости, связанные с переполнением буфера.

```void
struct InventoryItem {
    u64 item_uuid;          // Уникальный 64-битный мировой идентификатор (генерируется сервером)
    u32 item_id;            // Статический идентификатор типа (например: 0x0001 = патрон 9мм, 0x0A12 = дробовик)
    u16 quantity;           // Текущее количество предметов в стаке (максимум 65535)
    u8  is_equipped;        // Флаг состояния: 0x00 = в рюкзаке, 0x01 = экипировано персонажем в UZDoom
    u8  container_slot;      // Индекс ячейки внутри рюкзака или склада базы
    u32 durability;         // Текущая прочность предмета (для оружия и брони из Fallout-механики)
    u32 custom_data_ptr;    // 32-битный указатель в Ghost-RAM на структуру процедурных свойств пушки
    u32 security_checksum;  // CRC32 контрольная сумма полей предмета + MASTER_HWID для защиты от подмены
}
```

### 2.1 Защита структуры от модификации (Anti-Cheat Layer)
При изменении любого значения (например, при выстреле уменьшается `quantity`), рантайм `void.run` выполняет следующие действия:
1. Высчитывает новый хэш `CRC32(item_uuid + item_id + quantity + MASTER_HWID)`.
2. Сверяет его с текущим `security_checksum`. Если значения не совпадают (была попытка подмены количества патронов в ОЗУ через сторонний софт), вызывается защитный протокол `sys.fake_panic` из [PLAN.md](../Lang_for_my_decisions/PLAN.md).

## 🔄 3. Алгоритм безопасного P2P-обмена в игре (Secure Trade Protocol)

Торговля между игроками в кооперативном режиме (описанном в [MULTIPLAYER_SPEC.md](./MULTIPLAYER_SPEC.md)) защищена от уязвимостей типа "двойная трата" (Double Spend) или обрыва соединения во время транзакции с помощью протокола двухфазной фиксации (Two-Phase Commit).

```

    [Игрок А (Инвентарь в ОЗУ)]               [Игрок Б (Инвентарь в ОЗУ)]
                │                                         │
                ├─── 1. Заморозка слотов обмена в ОЗУ ────┤ (Ghost-RAM Lock)
                │                                         │
                ├─── 2. Верификация контрольных сумм ─────┤ (CRC32 Check)
                │                                         │
                ├─── 3. Оба игрока нажали "Принять" ──────┤ (Commit Phase)
                │                                         │
                ▼                                         ▼
    [Запись в sql.core] ─────────────────────── [Запись в sql.core]
    (Атомарное обновление секторов HiddenVault на дисках обоих игроков)

```


1. **Фаза инициализации (Lock):** Как только открывается окно обмена, выбранные слоты инвентаря Игрока А и Игрока Б блокируются в Ghost-RAM функцией `memory.lock_item_slots()`. Эти предметы нельзя выбросить, экипировать или продать торговцам.
2. **Фаза верификации (Prepare):** Рантайм хоста проверяет легитимность `item_uuid` обоих предметов через базу данных [sql.core](../Lang_for_my_decisions/sql.core). Если предметы существуют и их контрольные суммы верны, кнопка «Подтвердить сделку» становится активной.
3. **Фаза фиксации (Commit):** Когда оба игрока нажимают кнопку подтверждения, `void.run` одновременно (атомарно) выполняет транзакцию: удаляет UUID предметов из таблицы Игрока А и перезаписывает их в таблицу Игрока Б. Если во время этого процесса один из игроков выдернет сетевой кабель, транзакция полностью откатывается назад, возвращая предметы владельцам и исключая дюп.

## 📱 4. Синхронизация со Складом Гильдии и Приложением-компаньоном

Одной из ключевых особенностей системы является возможность удаленного управления ресурсами баз снабжения (концепция *State of Decay 2*), задокументированная в мобильном компаньоне [COMPANION_APP.md](./COMPANION_APP.md).

### 4.1 Алгоритм удаленной передачи ресурсов на склад базы
Игрок, находясь на работе или в пути, может открыть приложение на Android, зайти в свой инвентарь и перенести собранные за прошлую игровую сессию материалы (металл, дерево, патроны) на общий склад клановой базы ([CLAN_SPEC.md](./CLAN_SPEC.md)).

1. Визуальный интерфейс [View/](../Lang_for_my_decisions/View/) формирует пакет запроса на перемещение предмета.
2. Локальный мобильный рантайм `void.run` считывает зашифрованный файл сохранения инвентаря из `HiddenVault` смартфона.
3. Предмет упаковывается в сетевой пакет `MobileChatPacket`, подписывается цифровой подписью устройства и отправляется через бэкенд-хаб `deploy_hub.vc`.
4. Бэкенд пересылает пакет на выделенный сервер игры ([MULTIPLAYER_SPEC.md](./MULTIPLAYER_SPEC.md)). Сервер удаляет предмет из личного списка игрока и инжектирует его в общую базу данных склада клана.
5. Когда игрок вернется домой и запустит игру на ПК, UZDoom мгновенно отобразит обновленный инвентарь рюкзака и пополненные ресурсы на складе базы.

## 🛠️ 5. Разбор предметов и крафт (Fallout 4 Style Scrap Logic)

Любое найденное в мире оружие низкого качества (класса `RARITY_COMMON` из [WORLD_DESIGN.md](./WORLD_DESIGN.md)) игрок может разобрать прямо на ходу через консольное меню или интерфейс верстака.

* **Алгоритм деструкции предметов:** При вызове команды разбора, структура `InventoryItem` уничтожается в ОЗУ. Вместо нее лут-движок рассчитывает детерминированное количество базовых компонентов (компонент `Scrap_Metal` = `item_id: 0x00F1`, компонент `Circuit_Board` = `item_id: 0x00F2`).
* **Обновление чанка базы:** Полученные материалы автоматически направляются в хранилище текущего чанка открытого мира, изменяя дельта-пакет сохранений в [WORLD_DESIGN.md](./WORLD_DESIGN.md), что позволяет мгновенно использовать их для строительства стен или турелей защиты.
