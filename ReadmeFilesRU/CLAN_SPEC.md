# 🎖️ Спецификация ролевой системы персонажа, кланов и гильдейских перков (CLAN_SPEC.md)

Статус: **целевой дизайн, не реализованная подсистема**. Общая сверка: [PROJECT_STATUS.md](./PROJECT_STATUS.md) / [PROJECT_STATUS.v2](./PROJECT_STATUS.v2); размеры схем: [SERIALIZATION_SPEC.md](./SERIALIZATION_SPEC.md) / [SERIALIZATION_SPEC.v2](./SERIALIZATION_SPEC.v2) (срез токена не считается утвержденным без записи в `sql.core` и `memory.ctos`).

Настоящий документ содержит исчерпывающее техническое и архитектурное описание ролевой системы выжившего, механики формирования кланов (гильдий) и системы распределения перков. Система спроектирована на базе синергии трех игровых концепций: поуровневой прокачки и модификации параметров персонажа из **Fallout 4 / Fallout 76**, социального взаимодействия и кланового менеджмента из **State of Decay 2**, а также сетевой синхронизации ролей и рангов из **Borderlands 2**.

Главная цель данной подсистемы — связать социальную активность игрока в мобильном приложении-компаньоне с его боевой эффективностью внутри игрового движка UZDoom, защитив при этом данные прогресса от модификации на стороне клиента.

---

## 🏗️ 1. Системные и архитектурные связи

Подсистема персонажей и кланов является связующим ядром между боевой сессией и социальной экосистемой KINII:
* **Аутентификация рангов:** Проверка прав лидера клана или офицеров на выполнение административных действий жестко привязана к аппаратному хэшу устройства `MASTER_HWID` в конфигураторе [main.vc](../Lang_for_my_decisions/main.vc).
* **Защита прогресса:** Текущие очки опыта (XP), уровень и древо открытых перков удерживаются в зашифрованных структурах Ghost-RAM через [memory.ctos](../Lang_for_my_decisions/memory.ctos) (ссылка на ветку: [://github.com](https://://github.com)).
* **Персистентность клана:** Таблицы участников, казначейство и уровни баз записываются в скрытые транзакционные таблицы накопителя через [sql.core](../Lang_for_my_decisions/sql.core) (ссылка на ветку: [://github.com](https://://github.com)).
* **Стриминг чата:** Общение внутри клановых каналов перехватывается, шифруется сквозным методом (E2EE) и маршрутизируется сетевым мостом [bridge.ctos](../Lang_for_my_decisions/bridge.ctos) (ссылка на ветку: [://github.com](https://://github.com)).
* **Управление со смартфона:** Полноценный интерфейс администрирования клана, исключающий необходимость перегружать HUD игры, описан в [COMPANION_APP.md](./COMPANION_APP.md) и [SOCIAL_MESSENGER_SPEC.md](./SOCIAL_MESSENGER_SPEC.md).

## 📊 2. Бинарная структура профиля и кланового пакета

Данные персонажа и его принадлежности к клану сериализуются в компактные бинарные блоки для минимизации сетевого оверхеда при синхронизации между сервером, игрой и смартфоном. Правила выравнивания (padding) описаны в общем документе.

### 2.1 Структура персонажа (Player Profile Layer) — 64 bytes packed / 64 bytes native x64
```void
struct PlayerProfile {
    u32 player_id;            // Уникальный сетевой идентификатор учетной записи
    u32 clan_id;              // ID клана (0x00000000 = без клана)
    u16 character_level;      // Текущий уровень персонажа (Fallout-механика скейлинга)
    u64 current_xp;           // Текущее количество очков опыта
    u8  attr_special[7];      // Массив базовых характеристик S.P.E.C.I.A.L.
    u8  _padding[1];          // Выравнивание до 8-байтовой границы для native x64
    u64 unlocked_perks_mask;  // 64-битная маска открытых перков (каждый бит = конкретный навык)
    u32 faction_rep;          // Очки репутации внутри фракций открытого мира
    u32 integrity_hash;       // CRC32 хэш для валидации структуры рантаймом void.run
}
```

### 2.2 Структура кланового узла (Clan Node Layer) — 120 bytes packed / 128 bytes native x64
```void
struct ClanNode {
    u32 clan_id;              // Уникальный хэш-ID гильдии в sql.core
    char clan_name[32];       // Текстовое название клана (UTF-8, фиксировано 32 байта)
    u32 leader_player_id;     // Идентификатор создателя/владельца клана
    u16 clan_level;           // Уровень клана (прокачивается общим вкладом XP)
    u8  _padding_64[2];       // Выравнивание до границы u64 структуры
    u64 clan_xp;              // Общий накопленный опыт гильдии
    u64 vault_resources[4];   // Массив общих материалов казны (Металл, Дерево, Топливо, Медикаменты)
    u32 global_buff_flags;    // Флаги активных общеклановых перков, влияющих на игровой мир
    u32 structure_crc32;      // Контрольная сумма для проверки целостности в Ghost-RAM
}
```

## ⚡ 3. Механика динамического инжекта перков в движок UZDoom

Классический движок Doom работает на фиксированных константах (скорость перемещения актеров, урон оружия). Наша подсистема модифицирует поведение движка налету в зависимости от битовой маски `unlocked_perks_mask` профиля игрока.

### 3.1 Алгоритм перехвата тикера перемещения (Movement Hook)
При обработке физического кадра игрока в модуле UZDoom (`P_PlayerThink`):
1. Код игры делает запрос к рантайму KINII через `bridge.ctos`: `Kinii_GetActiveBuffs(player_id)`.
2. Если в маске `unlocked_perks_mask` взведен бит `#3` (Перк «Спринтер пустоши»), рантайм возвращает модификатор скорости \(M_{speed} = 1.25\).
3. Игра умножает базовые константы `FORWARDMOVE` и `SIDEMOVE` на \(M_{speed}\), обеспечивая динамическое изменение динамики движения персонажа без изменения исходного ядра рендерера.

### 3.2 Алгоритм расширения лимитов строительства базы
Если игрок активирует перк «Архитектор гильдий» (Влияет на `WORLD_DESIGN.md`):
* Максимальный радиус установки LineDefs стен вокруг центрального ядра базы расширяется на +1024 юнитов.
* База данных `sql.core` открывает доступ к инжекту сложных чертежей (например, тяжелых автоматических турелей, описанных в спецификации открытого мира).

## 📱 4. Социальное администрирование через Приложение-компаньон

Все рутинные функции управления гильдией полностью вынесены на сторону смартфона ([COMPANION_APP.md](./COMPANION_APP.md)), разгружая интерфейс игры на ПК.

```text
[Анкета кандидата на Android] ──(Подача заявки)──> [deploy_hub.vc (Бэкенд-Хаб)]
              │
      (Валидация подписи)
              │
              ▼
  [Выделенный Сервер Игры] <──(Обновление роли)─── [bridge.ctos мост]
```

### 4.1 Протокол обработки входящих заявок (Chat-Recruitment Protocol)
1. Пользователь в мобильном приложении через интерфейсы конфигуратора `deploy_hub.vc` (папка [View/](../Lang_for_my_decisions/View/)) нажимает кнопку «Подать заявку в клан».
2. Бэкенд-хаб `deploy_hub.vc` пакует ID соискателя и перенаправляет системное сообщение в закрытую чат-комнату офицеров гильдии.
3. Лидер клана открывает мессенджер на смартфоне, видит профиль кандидата (`PlayerProfile`) и нажимает «Принять».
4. Мобильный рантайм `void.run` подписывает транзакцию цифровым ключом сессии и отправляет команду на сервер игры ([MULTIPLAYER_SPEC.md](./MULTIPLAYER_SPEC.md)).
5. Сервер через `sql.core` атомарно обновляет поле `clan_id` в таблице сохранения игрока. При следующем входе в игру персонаж автоматически появляется на базе клана с соответствующими правами доступа к сундукам.

### 4.2 Активация глобальных клановых баффов (World Modifiers)
Когда клан накапливает достаточно опыта для повышения `clan_level`, лидер гильдии может со смартфона распределить очки в древе клановых перков. 
При выборе перка «Глубокие карманы гильдии», флаг в поле `global_buff_flags` перезаписывается. Движок генерации предметов [INVENTORY_SPEC.md](./INVENTORY_SPEC.md) на сервере считывает этот флаг и автоматически увеличивает максимальный размер стака материалов для всех участников клана, находящихся в игре на ПК.
