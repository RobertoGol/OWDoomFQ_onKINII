# 🌉 Архитектурная спецификация сетевого моста (bridge.ctos)

Данный документ описывает структуру, логику и протоколы взаимодействия сетевого моста между игровым движком **UZDoom (C++)**, системным рантаймом **KINII (void.run)** и **Мобильным приложением-компаньоном**. 

Мост решает задачу бесшовного, безопасного и оптимизированного подключения игроков в кооперативе (а-ля *Borderlands 2*), работы выделенного сервера через консоль (а-ля *Battlefield*) и мгновенного дублирования игрового чата в зашифрованный мессенджер на смартфонах.

---

## 🛰️ 1. Модель сетевого подключения (Network Topology)

Поэтому имена вроде `KInii_GetActiveBuffs`, `sys_update_world_stream` и `loot_generate_drop` в других документах — предполагаемые точки интеграции, а не доступные символы библиотеки. Система поддерживает два режима работы, переключение между которыми происходит прозрачно для пользователя:

1. **Режим Listen Server (Кооператив Borderlands 2):**
   * Один из игроков становится хостом.
   * Рантайм `void.run` на машине хоста открывает локальный сетевой порт и начинает обрабатывать входящие пакеты от других клиентов.
   * Подключение происходит напрямую через p2p-инжектор, минуя необходимость ручной настройки маршрутизатора (проброса портов), благодаря интеграции с подсистемой `net.raw_inject`.

2. **Режим Dedicated Server (Масштаб Battlefield / Fallout 76):**
   * Легковесный бинарник запускается на сервере через консоль (команда `void_win.exe --server`).
   * Графическая подсистема рендеринга Vulkan/OpenGL полностью отключается.
   * Сервер выступает главным авторитарным арбитром: он считает физику, проверяет попадания пуль и генерирует сиды для спавна лута из файла `world_stream.void`.
   * Один процесс игры или отдельный процесс является авторитетом сессии. Он принимает команды клиентов, проверяет их и рассылает состояние. Остальные клиенты не получают право назначать себе урон, предметы или координаты.

## 🔒 2. Сквозное шифрование чата и защита данных (E2EE)

Трафик игрового и гильдейского чата является полностью приватным. Архитектура исключает возможность перехвата сообщений провайдером или сторонними лицами.

* **Внутриигровой Ghost-RAM буфер:** Все сообщения чата перед отправкой попадают в изолированную зону памяти, управляемую файлом `memory.ctos`. Ключи шифрования сессии генерируются на основе `MASTER_HWID` устройства и никогда не сбрасываются на жесткий диск в открытом виде.
* **Протокол шифрования:** Для приватных диалогов и чата групп используется сквозное асимметричное шифрование. Сообщение шифруется на стороне отправителя и может быть расшифровано только легитимным получателем (в игре или в мобильном приложении). Телефон общается с сервисом аккаунтов/событий и игровым сервером через определённый протокол. Он не подключается напрямую к памяти процесса UZDoom. Команды управления базой зависят от D-001; первый безопасный срез — read-only телеметрия.
* **Экстренная очистка (Panic Button):** При фиксации попытки отладки процесса (дампинга памяти чата), ядро KINII вызывает команду `sys.fake_panic`, которая мгновенно затирает буферы чата в Ghost-RAM нулями, предотвращая утечку переписки.

## 📱 3. Синхронизация и Минимальный контракт адаптера

Связка с приложением (мессенджер + социальный профиль игрока) построена на асинхронном обмене данными через промежуточный бэкенд-хаб. До реализации выбирать один вариант: стабильный C ABI shared library, отдельный процесс с IPC или генерируемый C++ модуль. Нельзя предполагать, что внешний `kinii build` уже создаёт DLL или поддерживает произвольный FFI.

```text
[UZDoom client] ── команды/входы ──> [authoritative session]
                                              │
                                      [chat/event service]
                                              │
                                      [Android companion]
```

```text
[Игрок в UZDoom] ──(Пишет в чат гильдии)──> [bridge.ctos]
│
(Шифрование и Отправка)
│
▼
[Центральный Хаб]
│
(Push-уведомление)
│
▼
[Смартфон с Android]
(Рантайм void.run / View)
```

### Контракт должен определять (Область | Обязательное правило):
* **Версия |** Явный ABI/version handshake; несовместимая версия отклоняется.
* **Владение памятью |** Кто выделяет и освобождает буферы; никаких указателей между процессами.
* **Типы |** Фиксированные ширины, endian/encoding; `f32` не считается доступным типом KINII без реализации.
* **Таймаут |** Коды ошибок, timeout, частичный отказ, безопасное отключение адаптера.
* **Потоки |** На каком потоке вызывается функция; запрет блокировать render tick неограниченно.
* **Лимиты |** Максимальный пакет, число событий, частота вызовов и backpressure.
* **Идентификаторы |** Persistent UUID и короткие session ID разделены (0-610).
* **Совместимость |** Golden samples + тесты encode/decode для каждой версии.

Минимальная последовательность разработки: `version handshake` + пустой `event` + один запрос состояния + одна команда мира + сохранение. Каждый шаг проверяется интеграционным тестом на реально собранном адаптере.

### 4.1 События и команды. Предлагаемые категории:
* **lifecycle:** init/shutdown/version;
* **world:** chunk entered/left, object changes, structure built/destroyed;
* **combat:** validated damage event, projectile spawned, hit resolved;
* **inventory:** item created/transferred/consumed, transaction result;
* **social:** chat message, clan event, base telemetry;
* **persistence:** save/delta request, commit result, recovery result.

Событие не должно содержать двусмысленный клиентский результат как истину. Например, клиент сообщает о выстреле и времени команды, а сервер проверяет оружие, боеприпас, траекторию и право действия.

## 🔒 4.2 Сеть и криптография

Для транспорта использовать обычные sockets и явный протокол. P2P может потребовать сигнальный сервис, UDP hole punching, STUN/TURN; это не реализуется названием `net.raw_inject`.

### Разделять:
1. \*\*Шифрование транспорта\*\* между клиентом и сервером.
2. \*\*E2EE личных/групповых сообщений\*\*, где сервер не получает plaintext.
3. \*\*Аутентификацию команд\*\* и проверку прав пользователя.
4. \*\*Шифрование сохранений\*\* и управление ключами.

HWID не используется как секретный ключ. Нужны генерация ключей на устройствах, обмен публичными ключами, проверка отпечатков/pairing, ротация и отзыв. Для AES-GCM/ChaCha20-Poly1305 определить nonce, tag, associated data и обработку повторов. Форматы см. в [SERIALIZATION_SPEC.md](./SERIALIZATION_SPEC.md) и [SOCIAL_MESSENGER_SPEC.md](./SOCIAL_MESSENGER_SPEC.md).

## 💾 5. Хранение и износостойкость

Игровые сохранения и история чата хранятся в обычных пользовательских файлах/БД с версией формата, транзакцией или атомарной заменой, резервной копией и восстановлением. Принимаемый базовый вариант — D-001. Сырая запись в «битые» сектора не гарантирует сохранность и может повредить другие устройства.

Тесты обязаны покрывать обрыв питания/процесса между подготовкой и commit, повторный запуск, несовместимую версию и повреждённый пакет. Для торговли нужен один координатор authoritative state; две независимые записи на дисках разных игроков сами по себе не образуют атомарную транзакцию.

## 💾 6. Критерии готовности моста (HiddenVault)

* **Реализуемость кода (No-NanoBanana):**
  * собирается на заявленной платформе из зафиксированных исходников;
  * handshake и несовместимая версия проверены тестами;
  * модуль шифрует текст и передает его асинхронным потоком на бэкенд, описанный в `deploy_hub.vc`.
  * Бэкенд пересылает зашифрованный пакет на мобильное устройство (Android 10-15), где локальный рантайм KINII расшифровывает его и выводит на экран в интерфейсах папки `View/`.
  * **Обратная связь:** Если пользователь отвечает со смартфона, мессенджер отправляет пакет обратно на хаб, и `bridge.ctos` инжектирует текстовую строку прямо в консоль и чат запущенной игры UZDoom. Вместо имитации своего слоя очистки памяти/Log установить затронутую операцию, вернуть код ошибки, сохранить диагностический журнал без раздувания, перейти в read-only/offline режим при потере авторитета. Решение о завершении процесса принимается явно, а не маскируется под сбой ОС.
  * malformed/oversize input отклоняется без выхода за границы буфера;
  * права команд проверяются сервером;
  * секреты не попадают в логи;
  * вычисленная интеграция сохраняет поведение baseline UZDoom.

* **Хранение данных:**
  * История сообщений, профили друзей и настройки гильдии не хранятся в обычных текстовых или JSON файлах, которые легко отредактировать.
  * Запись истории ведется через движок данных `sql.core`.
  * Данные записываются в скрытые, намеренно помеченные как "битые" сектора диска (`HiddenVault`).
  * Доступ к истории чата имеет только авторизованный рантайм `void.run`, подтвердивший цифровую подпись BIOS.
  * Пока эти пункты не выполнены, документы не должны обещать работающий E2EE-мост, Ghost-RAM или защищённый dedicated-сервер.
